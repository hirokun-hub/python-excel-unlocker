# 要件定義書

## はじめに

本ドキュメントは、Excel パスワード解除ツールにおける日本時間（JST）対応機能の要件を定義します。現在、システムはすべての時刻表示をUTC（協定世界時）基準で行っているため、日本のユーザーにとって不自然な時刻表示となっています。本機能では、ユーザーが目にする時刻（ZIPファイル名、ZIP内ファイルの更新日時、ダウンロード時のLast-Modifiedヘッダー）を日本時間基準に統一し、UXを改善します。

重要な点として、内部ロジック（有効期限計算、ログ記録など）はUTCのまま維持し、システムの動作を変更しないことを前提とします。

## 用語集

- **JST（日本標準時）**: Japan Standard Time。UTC+9時間のタイムゾーン
- **UTC（協定世界時）**: Coordinated Universal Time。国際的な時刻の基準
- **ZipService（ZIP生成サービス）**: ZIP形式でファイルをアーカイブするサービスクラス
- **StorageService（ストレージサービス）**: ファイルの保存・取得を管理するサービスクラス
- **Last-Modified（最終更新日時ヘッダー）**: HTTPレスポンスヘッダーの一つで、リソースの最終更新日時を示す
- **ZipInfo（ZIP情報クラス）**: Pythonのzipfileモジュールで、ZIP内の各エントリのメタデータを管理するクラス
- **mtime（最終更新時刻）**: modification time。ファイルの最終更新日時
- **HTTP-date（HTTP日時形式）**: HTTPプロトコルで使用される日時形式（RFC 7231準拠、常にUTC表記）

## 要件

### 要件 1

**ユーザーストーリー:** ユーザーとして、一括ダウンロードで生成されるZIPファイルの名前に日本時間が表示されることを望みます。これにより、いつダウンロードしたファイルかを直感的に把握できます。

#### 受け入れ基準

1. WHEN システムが一括ダウンロード用のZIPファイルを生成する THEN システムは `解除済み_YYYYMMDD_HHMMSS_JST.zip` 形式のファイル名を作成しなければならない（タイムスタンプは日本標準時を表す）
2. WHEN システムがZIPファイル名用のタイムスタンプをフォーマットする THEN システムは区切り文字なしのYYYYMMDD_HHMMSS形式を使用しなければならない
3. WHEN システムがZIPファイル名にタイムゾーン表示を追加する THEN システムはファイル拡張子の前に `_JST` をサフィックスとして使用しなければならない
4. WHEN システムがタイムスタンプを生成する THEN システムはdatetimeに明示的なタイムゾーンオブジェクト（timezone.utcまたはZoneInfo('Asia/Tokyo')）を付与し、astimezone()メソッドでJSTに変換しなければならない
5. WHEN システムがファイル名を作成する THEN システムは `Z` や `+0000` などのUTC表示を含めてはならない

### 要件 2

**ユーザーストーリー:** ユーザーとして、ZIPファイルを解凍したときに各ファイルの更新日時が日本時間として表示されることを望みます。これにより、ファイルの作成時刻を自然に理解できます。

#### 受け入れ基準

1. WHEN ZIP生成サービスがZIPアーカイブにファイルを追加する THEN ZIP生成サービスはファイルエントリのdate_timeを日本標準時に設定しなければならない
2. WHEN ZIP生成サービスがZIP情報クラスオブジェクトを作成する THEN ZIP生成サービスはdate_timeタプルをJSTを表すように明示的に設定しなければならない
3. WHEN ZIP生成サービスがZipInfo.date_timeに値を設定する THEN ZIP生成サービスはtz-awareなUTC時刻をdt.astimezone(JST).timetuple()[:6]でタプル化してZipInfo.date_timeに渡さなければならない
4. WHEN ZIP生成サービスがnaive時刻を受け取る THEN ZIP生成サービスはそれをUTCとして扱い、replace(tzinfo=UTC)で補正してからJSTへ変換し、その後タプル化しなければならない
5. WHEN ユーザーが自分のシステムでZIPファイルを解凍する THEN 解凍されたファイルは日本標準時に対応する更新日時を表示しなければならない
6. WHEN ZIP生成サービスがファイルメタデータを書き込む THEN ZIP生成サービスはタイムスタンプ値を制御するために単純なwriteメソッドではなくZIP情報クラスオブジェクトを使用しなければならない
7. WHEN システムがJSTタイムスタンプを計算する THEN システムはdatetimeに明示的なタイムゾーンオブジェクト（timezone.utcまたはZoneInfo('Asia/Tokyo')）を付与し、astimezone()メソッドでJSTに変換しなければならない

### 要件 3

**ユーザーストーリー:** ユーザーとして、個別ファイルをダウンロードしたときにブラウザやOSが表示する保存時刻が日本時間であることを望みます。これにより、ダウンロード履歴を自然に管理できます。

#### 受け入れ基準

1. WHEN ダウンロードエンドポイントがファイルを返す THEN ダウンロードエンドポイントはHTTPレスポンスにLast-Modifiedヘッダーを含めなければならない
2. WHEN システムがLast-Modifiedヘッダーを設定する THEN システムはストレージサービスが返すUTC基準の最終更新時刻（信頼できる情報源）を基準として使用しなければならない
3. WHEN システムがLast-Modifiedヘッダーをフォーマットする THEN システムはUTC基準の最終更新時刻から直接HTTP-date形式（UTC/GMT表記）を生成しなければならない
4. WHEN システムがHTTP-dateを生成する THEN システムはemail.utils.format_datetime(dt.astimezone(UTC), usegmt=True)等のRFC 7231準拠フォーマッタを使用し、GMT表記に固定しなければならない
5. WHEN システムがLast-Modified生成を実行する THEN システムは中間でJSTに変換する必要はなく、UTC基準のmtimeから直接HTTP-date（UTC/GMT表記）を生成しなければならない
6. WHEN ストレージサービスがファイルメタデータを提供する THEN ストレージサービスはtz-awareなUTCのdatetimeとしてファイル最終更新時刻を返さなければならない（naiveは禁止）
7. WHEN ストレージサービスがnaive時刻を受け取る THEN ストレージサービスはそれをUTCとみなし、replace(tzinfo=UTC)で明示的に補正してからJST/HTTP-date処理に渡さなければならない

### 要件 4

**ユーザーストーリー:** システム管理者として、内部ロジック（有効期限計算、ログ記録）がUTCのまま維持されることを望みます。これにより、システムの動作が変更されず、既存の機能が正常に動作し続けます。

#### 受け入れ基準

1. WHEN システムがファイルの有効期限を計算する THEN システムはすべての内部計算でUTCを使用し続けなければならない
2. WHEN システムがイベントをログに記録する THEN システムはログエントリでUTCタイムスタンプを使用し続けなければならない
3. WHEN システムが有効期限チェックのためにタイムスタンプを比較する THEN システムはUTC基準の比較を使用しなければならない
4. WHEN システムが内部的にファイルメタデータを保存する THEN システムはストレージ層でUTC基準のタイムスタンプを維持しなければならない
5. WHEN システムが表示用のタイムゾーン変換を実行する THEN システムは基礎となるUTC基準のデータを変更してはならない

### 要件 5

**ユーザーストーリー:** 開発者として、タイムゾーン処理が環境に依存せず、明示的にJSTを扱うことを望みます。これにより、デプロイ環境が変わってもタイムゾーン表示が一貫します。

#### 受け入れ基準

1. WHEN システムがタイムゾーン変換を実行する THEN システムはシステム環境変数に依存するのではなく明示的なタイムゾーンオブジェクトを使用しなければならない
2. WHEN システムがJSTタイムスタンプを作成する THEN システムは固定のUTC+9オフセットを持つPythonのタイムゾーンライブラリを使用しなければならない
3. WHEN システムが異なる環境で実行される THEN システムはTZ環境変数に関係なく一貫したJSTタイムスタンプを生成しなければならない
4. WHEN システムがタイムゾーンオブジェクトを初期化する THEN システムは全サービスで共有する単一の定数（UTC = timezone.utc と JST = ZoneInfo('Asia/Tokyo')）を作成しなければならない
5. WHEN システムがタイムゾーン定数を定義する THEN システムは固定オフセット表現（timedelta(hours=9)等）や文字列直書き（'Asia/Tokyo'の都度記述）を禁止し、定数経由でのみアクセスしなければならない
6. WHEN システムがタイムゾーン処理をドキュメント化する THEN システムはどのタイムスタンプがJSTでどれがUTCかを明確に示さなければならない

### 要件 6

**ユーザーストーリー:** 開発者として、既存のテストが引き続き正常に動作することを望みます。これにより、JST対応による回帰バグを防ぎます。

#### 受け入れ基準

1. WHEN システムが既存のユニットテストを実行する THEN システムは変更なしですべてのテストに合格しなければならない
2. WHEN システムが統合テストを実行する THEN システムは既存のテストフィクスチャとの後方互換性を維持しなければならない
3. WHEN 新しいJST関連のコードが追加される THEN システムはタイムゾーン変換ロジックに対応するユニットテストを含めなければならない
4. WHEN システムがテストでZIPファイルを生成する THEN システムはタイムスタンプが正しくJSTに設定されていることを検証しなければならない
5. WHEN システムがテストでLast-Modifiedヘッダーを設定する THEN システムはHTTP日時形式が正しく、JSTの適切なUTC相当を表していることを検証しなければならない
6. WHEN JST対応のテストを実行する THEN テストは共通定数（JST/UTC）を経由した変換であることを検証しなければならない（例：ZipInfo.date_time書き込みとLast-Modified生成が同一定数を使用）
7. WHEN JST対応のテストでnaive入力を検証する THEN テストはnaive入力が渡された場合に例外を投げる、または少なくともテストで失敗として検知することを検証しなければならない（サイレント補正のみは禁止）
