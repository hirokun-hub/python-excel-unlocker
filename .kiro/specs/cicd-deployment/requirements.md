# CI/CD デプロイメント自動化 - 要件定義書

## はじめに

本ドキュメントは、Secure Excel Unlockアプリケーションの継続的インテグレーション・継続的デプロイメント（CI/CD）システムの要件を定義します。既存のGitHub ActionsワークフローをベースとしたAWS（バックエンド）とVercel（フロントエンド）への多環境デプロイメントシステムを対象とします。

## プロジェクト概要

### 背景
- Secure Excel Unlockアプリケーションの機能開発が完了
- 既存のGitHub ActionsによるCI/CDパイプラインが構築済み
- 多環境デプロイメント（development/staging/production）が実装済み
- 再利用可能ワークフローによる保守性の高い設計が採用済み

### 目的
- 既存CI/CDシステムの安定運用と継続的改善
- 多環境デプロイメントフローの最適化
- デプロイメント品質とセキュリティの向上
- 運用監視とトラブルシューティングの効率化

## 要件

### 要件1: 多環境デプロイメントフロー

**ユーザーストーリー:** 開発者として、ブランチ戦略に基づいた自動的な環境振り分けデプロイを期待する。そうすることで、適切な環境で段階的な検証を行いながら本番リリースできる。

#### 受入基準
1. WHEN developブランチにプッシュ THEN development環境に自動デプロイされる
2. WHEN mainブランチにプッシュ THEN staging環境に自動デプロイされる
3. WHEN production環境にデプロイ THEN 手動トリガー（workflow_dispatch）による承認が必要
4. WHEN プルリクエストが作成 THEN テストとビルドチェックのみ実行される（デプロイなし）

### 要件2: AWS バックエンドデプロイメント

**ユーザーストーリー:** 開発者として、バックエンドコードの変更が再利用可能ワークフロー（deploy-aws.yml）により自動的にAWS Lambdaに反映されることを期待する。そうすることで、環境別の一貫したデプロイメントが実現できる。

#### 受入基準
1. WHEN backend/配下のファイルが変更 THEN deploy-backend.ymlワークフローが実行される
2. WHEN デプロイが実行 THEN pytestによる単体テスト成功後にSAMデプロイが実行される
3. WHEN 認証方式 THEN GitHub OIDCまたはアクセスキーによる柔軟な認証が利用できる
4. WHEN 環境別デプロイ THEN excel-unlocker-api-dev/staging/prodスタック名で管理される

### 要件3: Vercel フロントエンドデプロイメント

**ユーザーストーリー:** 開発者として、フロントエンドコードの変更が段階的な検証（validate→build→deploy）を経てVercelに反映されることを期待する。そうすることで、品質を保ちながら効率的なデプロイメントが実現できる。

#### 受入基準
1. WHEN frontend/配下のファイルが変更 THEN validate-frontend.ymlによるLint/TypeCheckが実行される
2. WHEN 検証が成功 THEN build-frontend.ymlによる環境別ビルドが実行される
3. WHEN ビルドが成功 THEN deploy-vercel-reusable.ymlによるVercelデプロイが実行される
4. WHEN development環境デプロイ後 THEN e2e-test-frontend.ymlによるE2Eテストが実行される

### 要件4: 環境変数とシークレット管理

**ユーザーストーリー:** システム管理者として、機密情報を安全に管理しながらCI/CDパイプラインで利用したい。そうすることで、セキュリティを保ちながら自動化を実現できる。

#### 受入基準
1. WHEN AWS認証が必要 THEN GitHub OIDCまたはアクセスキーによる柔軟な認証が利用できる
2. WHEN Vercel認証が必要 THEN GitHub SecretsのVERCEL_TOKENが使用される
3. WHEN 環境別設定が必要 THEN NEXT_PUBLIC_API_URLが環境に応じて自動設定される
4. WHEN 機密情報が処理 THEN GitHub Secretsによる安全な管理が行われる

### 要件5: 包括的テスト自動化

**ユーザーストーリー:** 開発者として、段階的なテスト実行（単体→統合→E2E）により品質を保証したい。そうすることで、信頼性の高いデプロイメントが実現できる。

#### 受入基準
1. WHEN バックエンドが変更 THEN pytestによる単体テストが実行される
2. WHEN フロントエンドが変更 THEN ESLint/TypeCheck/Jestによる検証が実行される
3. WHEN development環境デプロイ後 THEN PlaywrightによるE2Eテストが実行される
4. WHEN deploy-full-stack.ymlが手動実行 THEN 統合テストまたは疎通確認が実行される
5. WHEN 通常の自動デプロイ（develop/mainプッシュ） THEN 統合テストは実行されない

### 要件6: 再利用可能ワークフロー設計

**ユーザーストーリー:** 開発者として、保守性の高い再利用可能ワークフローにより一貫したデプロイメントプロセスを利用したい。そうすることで、効率的な開発とメンテナンスが実現できる。

#### 受入基準
1. WHEN ワークフローが実行 THEN 呼び出し側と呼び出され側が明確に分離されている
2. WHEN GitHub Actions UIで確認 THEN 視覚的に進行状況が把握できる
3. WHEN 複数環境でデプロイ THEN 同一ワークフローで環境パラメータにより制御される
4. WHEN エラーが発生 THEN GitHub Actions Summaryで詳細な結果が確認できる

## 非機能要件

### セキュリティ要件
- **認証**: GitHub OIDCまたはアクセスキーによる柔軟なAWS認証
- **権限管理**: 最小権限の原則に基づくIAMロール設定
- **シークレット管理**: GitHub Secretsによる機密情報保護（VERCEL_TOKEN等）
- **監査ログ**: GitHub Actions実行ログによる操作記録

### パフォーマンス要件
- **ビルド時間**: 現実的な目標設定（フロントエンド検証・ビルド・デプロイで10分程度）
- **並列実行**: 再利用可能ワークフローによる効率的な処理
- **キャッシュ活用**: Node.js依存関係キャッシュによる高速化
- **条件分岐**: パス変更検出による不要な処理のスキップ

### 可用性要件
- **デプロイ成功率**: GitHub Actions標準の信頼性に依存
- **監視**: GitHub Actions UIとSummaryによる状況確認
- **通知**: GitHub標準通知機能の活用
- **ロールバック**: 手動でのworkflow_dispatch実行による対応

## 技術スタック

### CI/CDプラットフォーム
- **GitHub Actions**: メインのCI/CDプラットフォーム
- **GitHub OIDC**: AWSへの安全な認証
- **GitHub Secrets**: 機密情報管理

### デプロイメントツール
- **AWS SAM CLI**: バックエンドデプロイメント
  - development環境: excel-unlocker-api-dev
  - staging環境: excel-unlocker-api-staging  
  - production環境: excel-unlocker-api-prod
- **Vercel CLI**: フロントエンドデプロイメント
- **AWS CLI**: AWSリソース管理

### 監視・通知
- **GitHub Actions ログ**: デプロイメント状況確認
- **AWS CloudWatch**: Lambda関数監視
- **Vercel Analytics**: フロントエンド監視

## 制約事項

### 技術的制約
- GitHub Actions実行時間制限（6時間）
- AWS Lambda同時実行数制限
- Vercel無料プランの制限

### 運用制約
- developブランチ→development環境、mainブランチ→staging環境の自動デプロイ
- production環境は手動トリガー（workflow_dispatch）による承認制
- プルリクエストベースの開発フロー必須

### セキュリティ制約
- GitHub OIDCまたはアクセスキー認証の適切な設定必須
- IAMロールの適切な権限設定必須
- GitHub Secretsによる機密情報管理必須

## 成功指標（KPI）

1. **デプロイ頻度**: 現在の開発ペースに応じた適切な頻度
2. **デプロイ成功率**: GitHub Actions標準の信頼性レベル
3. **リードタイム**: 現実的な処理時間（バックエンド3-5分、フロントエンド8-12分）
4. **復旧時間**: 手動対応による迅速な復旧
5. **ワークフロー保守性**: 再利用可能設計による効率的なメンテナンス

### 現在の実測値（2025年1月24日時点）
- **バックエンドデプロイ**: 3-5分（pytest + SAMデプロイ）
- **フロントエンドデプロイ**: 8-12分（検証 + ビルド + デプロイ + E2E）
- **フルスタック手動デプロイ**: 10-15分（統合テスト含む）
- **キャッシュヒット率**: Node.js/Python依存関係で高効率

## 対象外範囲

以下の機能は現在の実装対象外とします：

1. **高度な監視**: リアルタイム監視やアラート機能
2. **自動ロールバック**: 障害検出による自動復旧
3. **A/Bテスト**: 機能フラグやカナリアデプロイ
4. **パフォーマンステスト**: 負荷テストや性能測定
5. **マルチリージョンデプロイ**: 単一リージョン（ap-northeast-1）のみ対象
