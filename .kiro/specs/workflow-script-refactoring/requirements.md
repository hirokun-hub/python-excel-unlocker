# GitHub Actions ワークフロー スクリプト リファクタリング - 要件定義書

## はじめに

本ドキュメントは、GitHub Actions ワークフロー内のインライン Python コードを外部スクリプトファイルに移行し、GitHub Actions 関連の Python スクリプトを `.github/scripts/` ディレクトリに統一して保守性を向上させる機能の要件を定義します。現在、`build-frontend.yml` 内にインライン Python コードが存在し、また複数の GitHub Actions 関連スクリプトが `scripts/` ディレクトリに分散配置されています。

## プロジェクト概要

### 背景
- GitHub Actions ワークフロー内にインライン Python コードが存在
- GitHub Actions 関連の Python スクリプトが `scripts/` ディレクトリに分散配置
- 同じ処理を行う外部スクリプトファイルが既に存在（重複）
- ワークフローファイルの可読性が損なわれている
- スクリプトの配置場所が統一されていない

### 目的
- インライン Python コードを外部スクリプトに統一
- GitHub Actions 関連スクリプトを `.github/scripts/` に集約
- コードの重複を解消し、保守性を向上
- ワークフローファイルの可読性を改善
- スクリプト管理の効率化と一貫性の確保

## 要件

### 要件1: インライン Python コードの外部化

**ユーザーストーリー:** 開発者として、GitHub Actions ワークフロー内のインライン Python コードが外部スクリプトファイルに移行されることを期待する。そうすることで、コードの重複を解消し、保守性を向上できる。

#### 受入基準
1. WHEN build-frontend.yml が実行される THEN インライン Python コードではなく外部スクリプトが呼び出される
2. WHEN 外部スクリプトが実行される THEN 既存のインライン Python コードと同じ処理結果が得られる
3. WHEN スクリプトが失敗する THEN 適切なエラーメッセージが表示される
4. WHEN ワークフローを確認する THEN インライン Python コードが削除されている

### 要件2: 既存スクリプトの活用

**ユーザーストーリー:** システム管理者として、GitHub Actions 関連の Python スクリプトを `.github/scripts/` ディレクトリに統一して管理したい。そうすることで、ワークフロー関連スクリプトを適切な場所に整理し、一貫性のある管理体制を構築できる。

#### 受入基準
1. WHEN ワークフローが実行される THEN `.github/scripts/` 配下のスクリプトが使用される
2. WHEN スクリプトが実行される THEN 移動したスクリプトの処理ロジックが変更されずに使用される
3. WHEN エラーが発生する THEN スクリプトファイルの標準的なエラーハンドリングが適用される
4. WHEN GitHub Actions 関連スクリプトを確認する THEN 全て `.github/scripts/` に統一されている

### 要件3: ワークフローの可読性向上

**ユーザーストーリー:** 開発者として、ワークフローファイルがシンプルで読みやすくなることを期待する。そうすることで、CI/CD パイプラインの理解と保守が容易になる。

#### 受入基準
1. WHEN ワークフローファイルを確認する THEN 複数行のインライン Python コードが削除されている
2. WHEN ステップ名を確認する THEN 処理内容が明確に表現されている
3. WHEN コマンドを確認する THEN 単一行のスクリプト呼び出しになっている
4. WHEN ワークフローを読む THEN 処理の流れが理解しやすい

### 要件4: 機能の互換性保証

**ユーザーストーリー:** DevOps エンジニアとして、リファクタリング後も既存の機能が正常に動作することを期待する。そうすることで、CI/CD パイプラインの安定性を保てる。

#### 受入基準
1. WHEN リファクタリング後のワークフローが実行される THEN Vercel プロジェクト設定の正規化が正常に行われる
2. WHEN project.json ファイルが存在する THEN rootDirectory の設定が適切に更新される
3. WHEN project.json ファイルが存在しない THEN 適切なエラーメッセージで処理が停止する
4. WHEN 処理が完了する THEN 既存の動作と同じ結果が得られる

### 要件5: エラーハンドリングの統一

**ユーザーストーリー:** システム管理者として、エラーハンドリングが統一された形で実装されることを期待する。そうすることで、問題発生時の対応が効率化される。

#### 受入基準
1. WHEN スクリプトファイルが存在しない THEN 明確なエラーメッセージが表示される
2. WHEN Python 実行環境に問題がある THEN 適切なエラーメッセージが表示される
3. WHEN スクリプト実行が失敗する THEN ワークフローが適切に停止する
4. WHEN エラーが発生する THEN GitHub Actions のログで詳細が確認できる

### 要件6: GitHub Actions カスタムアクション内スクリプトの統一

**ユーザーストーリー:** DevOps エンジニアとして、GitHub Actions カスタムアクション内で使用されている Python スクリプトも `.github/scripts/` に統一したい。そうすることで、全ての GitHub Actions 関連スクリプトが一箇所で管理できる。

#### 受入基準
1. WHEN カスタムアクションが実行される THEN `.github/scripts/` 配下のスクリプトが呼び出される
2. WHEN スクリプトパスが更新される THEN カスタムアクションの動作が変更されない
3. WHEN エラーが発生する THEN 適切なエラーメッセージが表示される
4. WHEN カスタムアクションを確認する THEN スクリプト参照パスが統一されている

### 要件7: 将来の拡張性確保

**ユーザーストーリー:** 開発者として、将来的に他のインライン コードも外部化しやすい構造になることを期待する。そうすることで、継続的な改善が可能になる。

#### 受入基準
1. WHEN 他のワークフローでインライン コードが発見される THEN 同様の手法で外部化できる
2. WHEN スクリプトディレクトリを確認する THEN 整理された構造になっている
3. WHEN 新しいスクリプトを追加する THEN 一貫した命名規則が適用されている
4. WHEN ドキュメントを確認する THEN スクリプト外部化の方針が記載されている

## 非機能要件

### 保守性要件
- **コードの重複排除**: インライン コードと外部スクリプトの重複を完全に解消
- **可読性向上**: ワークフローファイルの行数削減と構造の簡素化
- **統一性**: 他のワークフローとの一貫性を保持

### 互換性要件
- **機能互換性**: 既存の処理結果と完全に同じ動作を保証
- **エラー互換性**: 既存のエラーハンドリングと同等の品質を維持
- **実行環境互換性**: GitHub Actions 環境での正常動作を保証

### パフォーマンス要件
- **実行時間**: 既存のインライン実行と同等の処理時間を維持
- **リソース使用量**: 追加的なリソース消費を最小限に抑制
- **キャッシュ効率**: Python 環境のキャッシュ効果を活用
