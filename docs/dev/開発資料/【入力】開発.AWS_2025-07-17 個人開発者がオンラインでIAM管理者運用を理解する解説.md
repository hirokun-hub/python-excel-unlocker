
### 基本概念
- **[[AWS]]アカウント**  
  - 銀行口座のように「お金と設定」をまとめて管理する入れ物。  
  - 1つのアカウントには必ず **[[ルートユーザー]]**（登録メールアドレス＋パスワード）が存在。  
- **[[IAM]]（Identity and Access Management）**  
  - アカウント内で「誰が何をできるか」を細かく制御するサービス。  
  - **IAMユーザー**＝人・システムがログインする「IDカード」。  
  - **IAMロール**＝必要なときだけ借りる「制服」のような一時的権限。  

### なぜIAM管理者ユーザーを作るのか
| ルートユーザー                 | IAM管理者ユーザー              |
| ----------------------- | ----------------------- |
| すべての操作が可能。削除不可能。        | ポリシーで権限を制御でき、無効化・削除も可能。 |
| パスワード／[[MFA]]を破られると致命的。 | 万一侵害されてもルートで回復できる。      |
| ベストプラクティス：日常利用**禁止**。   | ベストプラクティス：日常利用**推奨**。   |

→ **自分1人でもルートは“金庫の鍵”、IAM管理者は“普段使いの鍵”** という整理が安全。  

### 個人開発の最小構成モデル
1. **ルートユーザー**  
   - 目的: 課金設定・サポートプラン変更・MFA再設定など“非常口”専用。  
   - 運用:  
     - [[MFA]]必須。  
     - 普段はログアウトし、アクセスキーは絶対に発行しない。  
2. **IAM管理者ユーザー（例: `IamAdmin`）** ← **今後ずっとメインで使う**  
   - 目的: 新規サービスの作成、権限管理などフル操作。  
   - 運用:  
     - 管理者権限ポリシー `[[AdministratorAccess]]` をアタッチ。  
     - Web コンソール／[[AWS CLI]] のクレデンシャルのローテーションを [[90]] 日ごと。  
3. **プロジェクト／環境ごとの IAM ロール**  
   - 目的: 実行環境や CI/CD など“アプリケーション”が借りる権限。  
   - 例: `ProjectA-LambdaRole`（最小限の[[Lambda]]権限）、`ProjectB-S3AccessRole` など。  
   - 運用:  
     - **[[IAMポリシー]]** で必要最小限の権限だけを付与。  
     - CLI / SDK からは **STS AssumeRole** で一時的トークンを取得。  

> **結論**  
> - **IAM管理者ユーザーは1つあれば十分**。プロジェクトごとに管理者を増やすと、かえって管理対象が増えリスクとなる。  
> - アプリ・自動化の権限分離は**IAMロール**で行い、IAM管理者は“鍵束の持ち主”として統制を取る。  

### プロジェクトごとに変えるべきもの
| 項目 | どこで分離するか | 補足 |
| --- | --- | --- |
| **請求の完全分離** | **[[AWS Organizations]] でアカウントを分ける** | 事業・チーム単位のコスト管理が必要な場合。 |
| **リソース名・タグ** | 同一アカウントでも OK | 例: `Project=A`, `Env=Prod` タグで検索性を確保。 |
| **権限** | IAMロールを分ける | Least Privilege 原則。 |

### 運用のヒント
- **CLI 作業は AWS [[SSO]] / [[IAM Identity Center]] の利用を検討**  
  - ブラウザで MFA → CLI へ一時トークンを払い出し、長期アクセスキーを排除できる。  
- **バージョン管理**  
  - [[CloudFormation]] / [[Terraform]] 等で IAM 定義を IaC 化すると構成ドリフトを防止。  
- **監査ログ**  
  - [[CloudTrail]] を必ず有効化し、S3 バケットに暗号化＋[[S3 Glacier]] で長期保管。  

### まとめ
- たとえ個人開発でも「ルートは金庫番」「IAM管理者は普段使い」という分担が基本。  
- IAM管理者ユーザーは**固定で1人**、プロジェクトごとにログインIDを増やさず、  
  **作業権限はロールで分割**するのが安全＆シンプル。  
- 将来チーム開発や複数事業へ拡張しても、この構成からスムーズにスケールできる。
